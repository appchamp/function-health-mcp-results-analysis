# Lab analysis: method and how to run it

Scripts for analyzing Function Health lab results exported by
[`function-health-mcp`](https://github.com/daveremy/function-health-mcp). They read the raw
export, classify every marker against **both** the lab's reference range and Function
Health's narrower optimal range, and build print-ready reports.

This folder holds code only. All personal data (the generated JSON and the written reports)
lives in a sibling `reports/` folder, kept out of this repository.

```
<parent>/
  lab-analysis/     this repo: analyze.py, md2html.py, render.sh, PROCESS.md
  reports/          personal: findings.json, merged-results.json, dated reports, HISTORY.md
```

---

## Quick run

```bash
node <path-to>/function-health-mcp/dist/cli.js sync   # pull latest data into ~/.function-health/exports/
python3 analyze.py                                     # write ../reports/merged-results.json + findings.json
```

`analyze.py` needs only Python 3. Options: `--quiet` skips the printed summary, and
`--out DIR` writes somewhere other than `../reports`. Keep `reports/` under its own (private)
version control so `git diff` there shows what changed between syncs.

The written reports are not generated by a script; they're written (by Claude, so far) from
`findings.json`, `merged-results.json` and the export's clinician notes. The `.md` is the
source, and the PDF is built from it:

```bash
python3 md2html.py ../reports/<name>.md      # -> ../reports/<name>.html (a throwaway build file)
./render.sh ../reports/<name>.html           # -> ../reports/<name>.pdf (headless Chrome)
```

Report naming: `<date written>-lab-analysis-v<N>.md`.

---

## Files

| File | Purpose |
|---|---|
| `analyze.py` | Reads every round in `~/.function-health/exports/*/results.json` and classifies each marker against both ranges |
| `md2html.py` | Converts a report `.md` to print-styled HTML (no dependencies) |
| `render.sh` | `./render.sh <file>.html` writes `<file>.pdf` next to it, using headless Chrome |

Output of `analyze.py`:

| File | Contents |
|---|---|
| `merged-results.json` | Every result from every round, normalized and classified. The source of truth |
| `findings.json` | Only the markers that need attention, grouped (see below), plus derived ratios |

---

## Why not rely on the MCP tools for this

Each result carries **two** ranges:

- `rangeString` (`referenceRange` in the output): the lab's **reference range**, which is wide.
  The `inRange` true/false flag is computed against it, and it's what the Function Health app flags.
- `optimalRange`: Function Health's own **optimal range**, which is much narrower. Nothing flags against it.

The MCP tools (`fh_summary`, `fh_results` with `status: out_of_range`) use only `inRange`, so
they report only markers outside the wide reference range. A marker can sit well outside its
optimal range and still read "in range". **Always classify against `optimalRange` from the raw
JSON.**

---

## Method details

- **`optimalRange` uses real interval notation.** `[a,b]` includes both ends, `(a,b)` excludes
  them, `[a,)` has no upper limit, `(,b]` has no lower limit. Parsing it as "two numbers"
  silently skips every range with only one limit. `parse_interval()` handles this.
- **Categories in `findings.json`:**
  - `flaggedOutOfRange`: `inRange` is false (outside the reference range)
  - `silentlySuboptimal`: `inRange` is true but outside the optimal range. Usually the main finding
  - `atOptimalEdge`: exactly on an optimal limit
  - `artifacts`: excluded because the stored optimal range is meaningless (the `ARTIFACTS`
    dict): a single point like `[5,5]`, an aspirational `[0,0]`, or a limit below what the
    lab can measure. Add to it when a new one appears.
- **Censored results:** some results are reported only as "<X" (below the lab's reporting
  limit). `calculatedResult` drops the "<", so the censoring is read from `displayResult`.
  These are marked `censored: true` and classified by `classify_censored()`, which says
  "below optimal" only when that's certain and "indeterminate" otherwise.
- **Derived values**, per round: HOMA-IR = glucose × insulin / 405 (above ~2.5 suggests
  insulin resistance) and triglycerides / HDL (above 3 is elevated in men).

## Other useful files in the export

All in `~/.function-health/exports/<round>/`:

- `notes.json`: clinician notes, one per category per requisition. They can include context the
  numbers don't (such as medications). **Check their claims against the data**: they have been
  seen to describe values as within optimal when they aren't.
- `biomarkers.json`: the biomarker catalog, with `sexDetails` (optimal ranges by sex). Many
  optimal ranges are marked `All` (unisex) and run low for men, notably hemoglobin,
  hematocrit and RBC count. For some markers the catalog range differs from the result's
  `optimalRange`; note the conflict rather than trusting either blindly.
- `pending-schedules.json`: upcoming visits, including the included follow-up (requisition
  type `FOLLOW_UP`) and its biomarker IDs. Map IDs to names via `biomarkers.json` and
  **compare by name**, because the catalog has duplicate IDs.
- `report.json`: per-marker records with a second set of optimal fields
  (`optimalRangeMin`/`Max`) that sometimes disagree with `optimalRange`.

## Setup gotchas

- **Login:** `function-health login --email … --password …`, or keep `FH_EMAIL`/`FH_PASSWORD`
  in `~/.env` (it does **not** read `.env` files in project folders). Google has blocked the
  token-refresh endpoint (`API_KEY_SERVICE_BLOCKED`), so the tool re-logs in from `~/.env`
  roughly hourly.
- **Sync crash:** through at least v0.5.6, `function-health-mcp` crashes at the end of a sync
  (`reading 'localeCompare'`) because clinician notes have no `id`. Use a build with the
  `sortById` fix in `src/diff.ts`.
- **Data changes without new tests:** Function Health sometimes edits old data (units,
  ranges). Re-run `analyze.py` after each sync and diff the output.
